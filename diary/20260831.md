# Terminal Infrastructure における Contract 境界の整理

今日は `terminal` のパッケージ構成について、`domain` / `infra` / `contract` の責務を改めて整理した。

もともとは `job_execution/terminal_runner/domain` に、Terminal Runner が利用するモデルや Protocol をまとめていた。しかし、実際の依存関係を追っていくと、この `domain` という名前には少し違和感があった。

現在の Terminal は `tool_execution/terminal` から利用される機能であり、Terminal Runner や Driver は、その機能を実現する Infrastructure として閉じ込めたい。

利用者から見れば、Runner や Driver の内部構造を知る必要はない。Terminal を利用するために必要な API だけが公開されていればよい。

一方で、Terminal Driver を追加したいアプリケーションや外部実装者には、Runner と Driver の間に存在する契約を知ってもらう必要がある。

## `TerminalDriverProtocol` の扱い

この問題を考えるうえで、`TerminalDriverProtocol` が重要な例になった。

`TerminalDriverProtocol` は Driver 実装者にとって必要な契約である。

通常の Terminal 利用者は、この Protocol を直接意識する必要はない。しかし、アプリケーション固有の Driver を実装して Terminal に登録したい場合には、この Protocol がなければ実装できない。

さらに `make_operations()` が返す `WaitOperation`、`WaitUntilOperation`、`RawStr`、`LineStr`、`InterruptionCode` なども、単なる Runner の内部実装ではない。

これらは Driver と Runner が互いに理解するための表現であり、外部 Driver 実装者が Driver を実装する際に必要となる可能性がある。

そのため、これらを通常の利用者向け API と同じ場所に置くのではなく、Infrastructure の拡張契約として切り出すことにした。

現在の構成は次のようになっている。

    tool_execution/terminal
    └── infra
        ├── contract
        ├── driver
        └── runner

## なぜ `contract` なのか

ここでいう `contract` は、Clean Architecture における既存の用語を置き換えるものではない。

Clean Architecture の `Port` / `Adapter` は、主として依存方向や責務を表現する。

一方、このプロジェクトで導入した `contract` は、

> Infrastructure を拡張する実装者が知る必要のある契約を明示するための境界

として定義する。

この違いは重要だった。

`Adapter` という分類だけでは、Pytoy が内部で提供する Adapter 実装と、外部の拡張者が実装するために参照する契約を、同じ Infrastructure の概念として扱うことになる。

また `Port` だけを基準にすると、Terminal の利用者が依存する API と、Terminal Infrastructure を拡張する実装者が依存する API を同じ「Port」として扱うことになり、利用者向け API と拡張者向け API の境界が表現しにくい。

そこで、Architecture 上の分類とは別に、「誰がその契約に依存するのか」という分類軸を持つことにした。

    依存方向・責務
          │
          ├── Port / Adapter
          │
          └── Clean Architecture 上の分類


    依存する人
          │
          ├── Terminal の利用者
          │       └── Public API
          │
          └── Infrastructure の拡張者
                  └── Contract

これは「Contract は Port ではない」という主張ではない。

ある Contract は、Clean Architecture の観点から Port と解釈できる場合もある。

重要なのは、

> Port であるかどうか

と

> 拡張者向け契約として扱うかどうか

は別の分類軸である、ということだ。

## 公開 API と Extension Contract の分離

この整理によって、`__init__.py` の役割も明確になった。

`infra/__init__.py` は、Infrastructure の利用者に公開する API を定義する。

一方、

`infra/contract/__init__.py`

は、Infrastructure を拡張する実装者が利用する契約を定義する。

したがって、`contract` に存在するすべての型を通常の利用者へ公開する必要はない。

また、通常の利用者が必要とする API と、拡張者が必要とする API を一つの公開面に無差別に並べる必要もない。

これは API の「公開／非公開」という一軸だけではなく、

- 機能を利用する人
- Infrastructure を拡張する人
- Infrastructure 内部で実装する人

という異なる依存者を意識して境界を作る、という考え方である。

## Protocol の配置を決めるルール

この考え方から、Protocol の配置についても単純なルールを採用できる。

「Protocol だから `domain` に置く」とは考えない。

代わりに、

> **誰がこの概念を知る必要があるのか？**

を確認する。

たとえば、ある Protocol が Infrastructure の内部実装同士の契約としてのみ必要であり、`tool_execution/terminal` の利用者には意味を持たないなら、Infrastructure の内部に閉じ込める。

外部 Driver 実装者が実装するために必要な Protocol なら、`infra/contract` に置く。

一方、Terminal の利用者自身が直接依存する抽象であれば、それは `infra/contract` に押し込めるのではなく、`tool_execution/terminal` の公開 API として扱う。

つまり、配置は「型の種類」だけで決めるのではなく、その型の依存者によって決める。

## `OutputJobProtocol` などへの適用

このルールは `TerminalDriverProtocol` に限らない。

たとえば `OutputJobProtocol` のような Protocol が今後必要になった場合も、

> その Protocol の影響範囲はどこまでか？

を基準に配置する。

それが `infra` の内部実装だけに閉じた契約なら、`infra` の外へ公開する必要はない。

逆に Infrastructure の拡張者が実装する必要があるなら、`infra/contract` に置く。

さらに、それを Terminal の通常利用者が知る必要があるなら、`tool_execution/terminal` 側の Public API として扱う。

この判断によって、Protocol の存在そのものを理由に不要なものまで `domain` に公開してしまうことを避けられる。

## 今回の設計で得られたこと

今回の整理によって、`domain`、`infra`、`contract` は単なるディレクトリ名ではなく、それぞれ異なる依存境界を表現するものになった。

特に `contract` は、Clean Architecture の代替概念ではない。

これは、

> **ライブラリ／フレームワークとしての拡張可能性を明示的に扱うための、プロジェクト固有の設計規約**

として位置づける。

Clean Architecture が主に「どちらがどちらに依存するか」を整理するのに対して、この規約ではさらに、

> **誰がその依存関係を必要としているのか**

を明示する。

この二つの観点を分離することで、利用者向け API、Infrastructure の内部実装、外部拡張者向け Contract が、同じ architectural boundary に存在するという理由だけで混ざってしまうことを防ぐ。

今回の `contract` 導入は、単なるディレクトリ整理ではなく、Infrastructure の拡張ポイントと Public API を明示的に分離するための設計上の判断である。



# Design Diary — Extension Boundary と `contract` の導入

今日は terminal execution 周辺のパッケージ構成について、大きな整理を行った。

これまで `job_execution` の下に置かれていた terminal runner / driver 周辺の概念を、
実際の利用単位である `tool_execution/terminal` の `infra` に集約する方向で整理した。

最初は `domain` / `protocol` / `models` という名前をそのまま維持する案もあったが、
「domain」という名前の下に、terminal package の利用者が知るべき概念と、
terminal の実装を拡張する人が知るべき契約が混在することが問題になった。

そこで `contract` という境界を導入した。

## `domain` と `contract` の役割

今回の設計では、概念を次のように分ける。

- `domain`
  - package の利用者が扱う、package 自体の概念
  - package の機能を利用するために知る必要があるもの

- `contract`
  - package の機能を拡張する実装者が知る必要のあるもの
  - extension author が実装するときに従わなければならない Protocol / 型 / データ構造
  - package 内部の実装と外部の拡張実装者との間で共有される契約

- `infra`
  - 実際の infrastructure implementation
  - 外部の実行環境や UI backend などへの具体的な適応を担当する

この `contract` は、Clean Architecture の標準用語としての `Port` と完全に同義ではない。

Clean Architecture の文脈では、一部の contract は Port と解釈できる。
しかし、今回の `contract` には、Port として扱うよりも、
「拡張実装者と内部実装が共有するための Protocol / 型」という性質のものも含まれる。

あえて `contract` という名前を採用したのは、
「この package の extension boundary である」という設計意図を、
ディレクトリ構造として明示するためである。

## なぜ Port ではなく `contract` としたのか

今回の構造では、少なくとも二種類の外部依存者が存在する。

1. package の機能を利用する人
2. package の infrastructure を拡張する人

従来の `domain/protocol` のような構造にすると、
この二者が依存する Protocol が同じ場所に集まりやすい。

しかし、両者は異なる方向から package と関わっている。

利用者が知るべき API と、
extension author が知るべき implementation contract は、
同じ「外部との境界」であっても意味が異なる。

`contract` を独立させることで、
「誰がこの型を必要としているのか」を構造上明示できる。

これは Clean Architecture の Port / Adapter という概念を否定するものではない。

むしろ、Clean Architecture の考え方を維持したまま、
plugin / extension architecture に必要な境界を追加で明示したものと考える。

## `TerminalDriverProtocol` が `contract` に入る理由

`TerminalDriverProtocol` は、単なる内部実装用 Protocol ではない。

外部の application / extension author が、
独自の terminal driver を実装して登録するために必要になる。

したがって、この Protocol は外部拡張者に公開されるべきであり、
`contract` の一部となる。

さらに `make_operations()` の返却値に使われる
`WaitOperation` や `WaitUntilOperation`、
`RawStr` / `LineStr`、
`Snapshot`、
`InterruptionCode` などについても、

「Protocol を実装するために外部実装者が意味を理解する必要があるか」

という観点で公開範囲を判断する。

Protocol が Public だからといって、
その Protocol が内部で参照するすべての型を自動的に Public にするわけではない。

しかし、外部実装者がその Protocol を実装する際に、
その型を生成・参照・解釈する必要があるなら、
それは実質的に extension contract の一部である。

## `infra/__init__.py` の役割

`infra/__init__.py` は、
infra の利用者に対する公開 API を定義する。

ここには、infra の外側から利用する必要があるクラスや型だけを公開する。

一方、`contract/__init__.py` は、
infra の実装を拡張する人が知る必要のある contract を公開する。

したがって、

    infra/__init__.py
        ↓
    infra の利用者

    infra/contract/__init__.py
        ↓
    infra の拡張実装者

という二つの境界を意識する。

## Protocol の置き場所について

Protocol であること自体は、配置を決める理由にはならない。

重要なのは、その Protocol が誰との境界を表しているかである。

例えば、

- 外部の Driver 実装者が実装する `TerminalDriverProtocol`
  → `contract`

- infra 内部の runner 実装差し替えのためだけに存在する Protocol
  → `infra` 内部

となる。

つまり、

    Protocol == contract

ではない。

    extension author が従う契約 == contract

という考え方を基本とする。

## 今後の整理方針

今後は、このルールを既存コードに適用していく。

特に LLM / coding agent に作業させる場合は、
単純なファイル移動ではなく、公開境界から依存関係をたどって判断させる。

例えば、

「この Protocol は外部 extension author に公開されているか？」
「その Protocol を実装するために外部から参照する必要がある型は何か？」
「その型は contract の一部として公開すべきか？」
「それとも infra 内部だけで完結しているか？」

という順番で確認する。

これにより、ディレクトリ構造そのものが
「誰が何に依存してよいか」を説明するようにする。

今回の整理の目的は、単にコードをきれいにすることではない。

API 境界と extension boundary を明確にし、
人間にも LLM にも、
「このコードを変更するとき、どこまで影響を考えればよいのか」
を読み取りやすくすることである。

一度このルールを確立できれば、
以後のリファクタリングは個別の設計判断ではなく、
設計原則を既存コードへ適用する作業に変えられる。

これは今後の開発速度だけでなく、
LLM coding agent による変更の安全性を高めるための基盤にもなる。
