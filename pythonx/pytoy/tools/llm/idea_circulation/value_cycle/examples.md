ValuableDemand 設計事例集

位置づけ: 旧 ValuableDemand モデルで作成した設計事例を保存し、今後の Demand モデルや value_cycle の設計を考えるための参照資料とする。
注意: 本資料は旧実装の仕様をそのまま新システムへ引き継ぐことを意味しない。以下の定義は、設計上の判断や選好を検討するための事例であり、必要に応じて再評価する。

1. 目的
旧実装では、成果物の種類に応じて ValuableDemand の内容を変え、何を作るか、何を満たすべきか、どのような品質を重視するかを表現していた。
この資料では、次の三つの事例を保存する。
- 短編小説
- Python 技術記事
- 数学の定理と証明
これらは同じ Demand の枠組みを使いつつ、成果物の分野によって成立条件や品質の意味が異なることを示している。

2. 共通の設計モデル
旧 ValuableDemand は、主に次の三つの要素を持っていた。
2.1 ValidityConditions
成果物が成立するために満たすべき最低条件を記述する。
これらの条件は品質の高さとは区別される。たとえば、文章が流暢であっても、技術的な説明が誤っていたり、数学的な証明に論理の飛躍があったりすれば、要求された成果物として成立していない可能性がある。
2.2 QualityCriteria
成立条件を満たした成果物を、複数の観点から評価するための基準を記述する。
品質基準は互いに競合する場合がある。すべての基準を同時に最大化できるとは限らず、成果物の目的や想定読者に応じた判断が必要になる。
2.3 Preference
依頼者や想定読者の選好、前提、優先順位を記述する。
Preference は、成果物が成立するための普遍的な条件とは限らない。複数の有効な成果物や実現方法がある場合に、どの方向性を優先するかを示す。
2.4 この区別の意義
三つの要素を分けることで、次のような違いを表現できる。
- 成立していない: 必須条件を満たしていない。
- 成立しているが、品質に課題がある: 成果物として成立しているものの、重要な品質基準を十分に満たしていない。
- 成立しており、選好にも合っている: 必須条件を満たし、品質基準と依頼者の選好にも適合している。
ただし、自由記述の基準だけでは、評価の一貫性や検証可能性が自動的に保証されるわけではない。実際の評価方法は、成果物の領域やリスクに応じて別途設計する必要がある。

3. 事例 A：短編小説
3.1 ValidityConditions
- 完成した短編小説が成果物として作成されている。
- 物語に一貫した前提、展開、結末がある。
- 単独の作品として読める。
- 二次創作の場合、元作品として認識できる程度に、指定された原作の特徴を尊重している。
3.2 QualityCriteria
- 物語の一貫性: 展開に整合性があり、物語として成立している。
- 人物の魅力: 登場人物が印象に残る。
- 独創性: 既存の作品や発想をなぞるだけでなく、独自の価値を持つ。
- ユーモア: 複数の概念を結びつけ、背後にある構造や意外な関係を見いだすことで面白さを生み出す。
- 作品の意図: 作品が読者に何を伝え、何をもたらそうとしているかが明確である。
- 原作への忠実さ: 二次創作の場合、原作の人物像や世界観を適切に扱っている。
3.3 Preference
- 二次創作では、登場人物を必要以上に増やさないことが望ましい。
- 原作の人物を表面的に扱うことは避け、少数の人物に焦点を当てて性格や内面を深く描くことを好む。
- 別々の原作に属する人物を組み合わせることで、新しい構造や面白さが生まれる場合がある。
3.4 設計上の所見
この事例では、物語として成立するための条件と、好ましい作品の方向性が区別されている。
たとえば、登場人物を少数に絞ることは、すべての短編小説に当てはまる必須条件ではない。ここでは依頼者の選好として扱われている。一方、物語の展開や結末に一貫性があることは、短編小説として成立するための条件に近い。
また、原作への忠実さは、二次創作では重要だが、原作から意図的に距離を取る作品では意味合いが変わる。したがって、この基準は作品の目的や二次創作としての位置づけを踏まえて解釈する必要がある。
ユーモア、独創性、原作への忠実さなどは、作品によって重要度が異なる。QualityCriteria に列挙されていることだけを理由に、すべての作品で同じ重みを持つと解釈してはならない。

4. 事例 B：Python 技術記事

4.1 ValidityConditions
- 完成した技術記事が成果物として作成されている。
- 技術的な主題と、記事が扱う範囲が明確に定義されている。
- 技術的な主張が十分に正確であり、対象となるソフトウェア、言語、システムの挙動や仕様と、認識しながら矛盾する説明をしていない。
- コード例が内部的に一貫しており、説明と対応している。
- 主張の理解に実質的な影響を与える前提、バージョン依存、プラットフォーム依存、制約が特定されている。
- 専門的な読者が、説明されていない必須の手順に頼らず技術的な主題を理解できるだけの説明がある。
4.2 QualityCriteria
- 技術的な深さ: 表面的な利用方法の説明にとどまらず、仕組みや根底にある原理を説明する。
- 技術的な精密さ: 用語、区別、説明が専門的な読者にとって十分に正確である。
- 実用性: 読者が設計判断、実装、デバッグ、実際の仕組みの理解に活用できる。
- 概念の明瞭さ: 複雑な仕組みが、相互関係を理解しやすい構造で説明されている。
- 例の有用性: コード例が単に構文を示すだけでなく、重要な挙動や概念を明らかにする。
- 境界条件への配慮: 関連する例外的な挙動や制約を適切に扱う。
- 抽象と実装の接続: 必要に応じて、概念的な説明と、プログラム、ランタイム、ライブラリ、OS、ハードウェアなどで実際に起きることを結びつける。
- 簡潔さ: 主題の理解に寄与しない説明を避ける。

4.3 Preference
想定読者は、経験豊富な Python 開発者またはソフトウェアエンジニアである。初心者向けのアクセシビリティは主要な目的ではなく、経験者にとっての深さと知的価値を優先する。
読者は、デザインパターンやドメイン駆動設計（DDD）などの設計原則に関心があると想定する。Python の実装と、より高い抽象度にある設計方針や原則を結びつける説明を特に歓迎する。また、他のプログラミング言語、機械学習、プロンプト／コンテキストエンジニアリングへの関心も想定する。
API の使い方を示すだけでなく、なぜその仕組みがそのように動くのかを説明することが望ましい。
有用であれば、Python の挙動を CPython の内部実装、C インターフェース、OS の仕組み、コンパイラの挙動、Rust との相互運用など、抽象度の境界をまたいで説明してよい。
関連性の薄い機能を広く浅く紹介するよりも、技術的に興味深い接続を掘り下げることを好む。
複数の実装方法が存在する場合は、推奨する方法のトレードオフと前提を明示することが望ましい。
想定する Python のバージョンは 3.12 以降である。
4.4 設計上の所見
この事例では、想定読者と記事の目的が品質の解釈を大きく左右している。
初心者向けの記事であれば、内部実装の詳細を省略することが理解の助けになる場合がある。一方、経験者向けの記事では、内部実装や抽象化の境界こそが記事の価値になることがある。そのため、「分かりやすさ」を単純に「説明を簡単にすること」と同一視していない。
また、技術的な正確さは、文章を生成した主体が自分で評価するだけでは保証できない。必要に応じて、公式ドキュメントの確認、コード実行、テスト、対象バージョンの検証など、外部の根拠を用いる必要がある。
この点は、品質基準そのものと、その基準を確認するための検証手段を区別すべきことを示している。

5. 事例 C：数学的な命題と証明
5.1 ValidityConditions
- 完成した数学的な命題と、その証明が成果物として作成されている。
- 命題の前提、定義、適用範囲が明示されているか、文脈から曖昧さなく確立されている。
- 証明に必要なすべての論理的な要所が正当化されている。
- 本質的な主張が、適切な根拠、定理、定義、または既に確立された結果による正当化なしに、証明済みとして扱われていない。
- 結論が明示された前提から導かれている。
- 数学的な記法が一貫しており、議論に実質的な影響を与える曖昧さを持ち込んでいない。
5.2 QualityCriteria
- 厳密さ: 議論の論理的な依存関係が十分に明確である。
- 明瞭さ: 論証の構造と目的が、想定する数学の読者に理解できる。
- 概念的な洞察: 命題が真であることを示すだけでなく、なぜ真であるのかを明らかにする。
- 優雅さ: 適切な場合、自然で簡潔、または洞察を与える論証を用いる。
- 一般性: 意味のある数学的価値が得られる場合、より一般的な原理を明らかにする。
- 簡潔さ: 本質的な推論を隠すことなく、不要な技術的手順を避ける。
- 教育的価値: 読者が数学的な考え方を学び、復習し、再構成する助けになる。
- 適切な抽象度: 数学的な主題と想定読者に適した抽象度で説明する。
- 関連性: 有用であれば、他の数学的概念、同値な定式化、関連する定理との関係を明らかにする。
5.3 Preference
標準的な想定読者は、大学学部から大学院程度の数学的背景を持つ。
主題が初等的なものである場合は、大学数学の基礎を高い水準で復習できるような、特に洗練された説明を目指す。
問題が本質的に難しい場合は、必要に応じて高度または研究レベルの数学的知識を利用してよい。ただし、説明されない高度な議論を、明瞭な論証の代わりに用いてはならない。
中心となる証明と、任意の補足、一般化、歴史的背景、他分野との関連は、区別して提示することが望ましい。
複数の証明がある場合、単に最短の導出を示す証明よりも、背後にある数学的構造を明らかにする証明を一般に好む。
概念的な明瞭さが大きく向上する場合は、簡潔さを多少犠牲にしてもよい。
5.4 設計上の所見
この事例では、論理的に正しい証明であることと、洞察に富んだ証明であることが明確に区別されている。
短い証明であっても、論理的な要所が正当化されていなければ成立条件を満たさない。一方、完全で正しい証明が、必ずしも最も優雅で教育的な証明であるとは限らない。
Preference は、複数の有効な証明の中からどの方向性を選ぶかを示している。これは、正しさを犠牲にして好みを優先するという意味ではなく、成立条件を満たす候補の間で、より望ましい説明を選ぶための指針である。

6. 三つの事例から得られる設計上の知見
6.1 共通の構造と領域固有の基準を分ける
三つの事例は、同じ三要素を使っている。
- 成果物として成立するための条件
- 成果物の品質を評価する観点
- 依頼者や読者が望む方向性
一方、具体的な基準は領域ごとに大きく異なる。数学の証明における論理的な正当化と、小説における人物の魅力を、同じ評価方法で判定することはできない。
したがって、共通化するべきなのは評価の枠組みであって、すべての分野に同じ品質基準を適用することではない。
6.2 成立条件と品質基準の優先順位を明確にする
旧モデルでは、ValidityConditions が QualityCriteria より優先されるという考え方を採用していた。
この考え方は、たとえば次のような判断に有用である。
- 論理的に不完全な証明を、文章の美しさだけで高く評価しない。
- 技術的な誤りを含む記事を、読みやすさだけで完成と見なさない。
- 物語として成立していない作品を、独創的な着想だけで完成と見なさない。
ただし、現実の評価では、どの条件が本当に必須なのかを慎重に定義する必要がある。厳しすぎる成立条件は、意図的な実験や新しい表現を不必要に排除する可能性がある。
6.3 品質基準は競合しうる
簡潔さと深さ、独創性と原作への忠実さ、一般性と説明の分かりやすさなどは、常に同時に最大化できるとは限らない。
品質基準を列挙するだけでは、競合時にどのような判断をするかは決まらない。必要に応じて、優先順位、想定読者、成果物の目的、許容できるトレードオフを明示する必要がある。
6.4 Preference は要求そのものと同一ではない
Preference は、複数の実現可能な選択肢の中から望ましい方向を選ぶために役立つ。一方で、すべての好みを必須条件として扱うと、成果物の選択肢を不必要に狭めてしまう。
また、AI が文脈から推測した好みと、人間が明示した好みは区別する必要がある。推測された選好を、本人が明示的に要求した条件であるかのように扱ってはならない。
6.5 基準を定義することと、基準を検証できることは別である
「技術的に正確である」「独創性がある」「証明が厳密である」といった基準を定義しても、それだけで適切な評価が実現するわけではない。
成果物の領域に応じて、次のような検証方法を組み合わせる必要がある。
- 技術記事: 公式資料、コード実行、テスト、バージョン確認
- 数学的証明: 論理の確認、既知の定理や定義との照合、必要に応じた形式的検証
- 創作: 人物像、物語構造、原作との関係、意図した読者体験の検討
すべての品質を機械的に数値化する必要はない。重要なのは、何を根拠に評価したのか、何が未確認なのかを可能な範囲で明らかにすることである。

7. 新しい設計へ引き継ぐ際の注意点
この資料は、旧 ValuableDemand モデルのコードを新しい構造へそのまま移植するための仕様書ではない。
今後の value_cycle の設計では、少なくとも次の点を改めて検討する。
1. Demand の構造: 成立条件、品質基準、選好をどのようなデータ構造で表現するか。
2. 根拠と検証: 各基準を何によって確認するのか。確認できていない場合、その状態をどう表現するか。
3. 人間の意図: 明示された要求と、文脈から推測された仮説をどのように区別するか。
4. 優先順位: 条件や品質基準が競合した場合、どのポリシーで判断するか。
5. 完了判定: 成果物が作成されたことと、期待した価値が実際に生じたことをどう区別するか。
6. フィードバック: 実行と評価から得られた学びを、どのように Artifact として保存し、次の判断に利用するか。
Demand の充足は、期待した価値が実現したことと同義ではない。成果物を完成させた後も、必要に応じて結果を検証し、期待した変化が生じたかを確認する必要がある。
この区別は、value_cycle が単なる成果物生成のパイプラインではなく、価値の実現と検証を繰り返す仕組みであるための重要な前提となる。

8. 位置づけのまとめ
本資料に含まれる三つの Demand は、旧モデルにおける具体的な設計事例である。
これらから引き継ぎたいのは、特定の Python クラスや関数の形そのものではない。主に、次の設計上の知見である。
- 成果物の成立条件、品質基準、選好は区別できる。
- 共通の評価構造を使いながら、領域ごとに異なる品質の意味を表現できる。
- 品質基準は競合することがあり、単純な最大化では扱えない。
- 人間が明示した要求と、AI が推測した選好を混同してはならない。
- 基準の定義と、その基準を検証する手段は別に設計する必要がある。
- 成果物の完成と、価値の実現は区別されるべきである。
旧実装は、これらの考え方を具体化した一つの形として保存する。今後の実装では、これらの知見を参照しながら、新しい責務の境界とデータモデルに適した形へ再構成する。
